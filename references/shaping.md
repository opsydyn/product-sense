# Shape a bounded bet

Start with the agreed problem and appetite. An appetite is a chosen spending limit, not an estimate of a predetermined design. If missing, propose one and label it.

Describe the core path sufficiently to expose risks while leaving implementation room. Include key dependency, failure and recovery route. Identify rabbit holes before commitment. State exclusions. Cut breadth before the quality needed for the user outcome.

For manual-first services, name operator role, response time, capacity, backup and failure handling. Show true state: requested differs from confirmed. Operator effort is a real cost. Set a trigger for automation based on load, delay or failures.

Respect a locked stack or promised capability. Use flexibility in scope, sequence and delivery. If the promise cannot fit, state the mismatch and offer concrete time or scope choices; do not quietly redefine completion.

State what the bet ends in:

- Discovery: a decision supported by new evidence.
- Delivery: a bounded working user path and measurement.
- Pilot: evidence of value under stated operational limits.

Define decision owner, next action, time box, scope and stop/reshape condition. If no owner is supplied, name the needed role, not an invented person. Carry unresolved assumptions into the handoff.

Sequence coherent actions: remove the main obstacle, verify progress, then widen if evidence warrants it. Novel technology is an option, not a reason to expand scope.
