# Human-centered design and design thinking

## Inspect a task

State goal, starting knowledge and context. Compare expected and actual behavior. Label expert inspection as inference; screenshots cannot establish real behavior or unseen states.

Apply Norman's lenses: distinguish possible actions from cues showing them; inspect control-to-result mapping, feedback, error-preventing constraints and the conceptual model formed by the experience. Explain a failure through a specific step, not “bad UX.” Put information in the world instead of requiring recall.

Check the journey from entry through first success, return, failure, recovery and exit. Include relevant loading, empty, pending, success and failure states. Preserve work during recovery. Check keyboard and assistive technology access, readable content and non-color cues where relevant. Preserve informed choice, cancellation and undo.

Write status copy from known system behavior. Give a supplied wait time when available; otherwise give a concrete status-check or recovery action. Do not invent confirmation, timing or email promises.

## Explore and narrow

Use the Double Diamond iteratively:

| Stage | Action | Exit evidence |
|---|---|---|
| Discover | Observe recent tasks and context | Credible problem patterns and contrary cases |
| Define | Select a user need and constraint | Testable problem frame |
| Develop | Sketch distinct routes, including service changes | Options addressing the same goal |
| Deliver | Test the smallest useful representation | Evidence for the next decision |

Balance human value, feasibility and business viability. Make low-cost artifacts to answer a question. Use a focused sprint for a consequential shared uncertainty; do not impose a five-day ceremony for a copy fix.

## Test and report

Give a realistic task without naming the control or teaching the flow. Observe first action, hesitation, status interpretation, completion and recovery. Ask what users expected after watching behavior. Cover relevant experience levels and access needs. Separate help from unassisted success.

For each finding state step, mismatch, consequence, evidence status, correction and verification. Rank blockers before friction and polish. Use a journey table for intent, touchpoints, visible state, operator responsibility and handoffs. Add a service blueprint when backstage operations affect the decision.

Teach domain knowledge where it builds capability. Fix hidden access, unclear controls and missing feedback before adding tours. Preserve useful expert paths without placing their complexity on beginners.
